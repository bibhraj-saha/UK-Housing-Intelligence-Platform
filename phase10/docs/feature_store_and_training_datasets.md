# Phase 10 Step 3: Feature Store and Training Datasets

## Purpose

Step 3 establishes the reproducible feature and training-data layer for the UK Housing Intelligence Platform machine-learning system.

The implementation converts analytical housing history into point-in-time feature datasets and chronologically split model-training artifacts.

## Architecture

The Step 3 data flow is:

1. Historical housing analytics source
2. Entity-month normalization
3. Point-in-time feature engineering
4. Feature-store materialization
5. Prediction-contract target construction
6. Leakage validation
7. Chronological train/validation/test splitting
8. Reproducible Parquet artifacts and manifests

## Entity and Time Keys

Primary entity:

- `lsoa_code`

Primary event timestamp:

- `period_end`

The feature store expects one row per LSOA and monthly period.

## Feature Store

The feature store contains historical features such as:

- 1-month price lag
- 3-month price lag
- 3-month shifted rolling price mean
- 3-month shifted rolling price standard deviation
- 1-month historical price growth
- 3-month historical price growth
- 1-month transaction lag
- 3-month shifted transaction rolling mean

Lagged and rolling features are constructed within entity boundaries.

Rolling features are shifted before aggregation so the current observation is not used in its own historical rolling feature.

## Prediction Contracts

Formal contracts are defined for:

- price prediction
- growth prediction
- area recommendation

The price and growth contracts currently use a 3-month horizon.

This horizon is aligned with the predictive data-gap assessment, which found approximately 11.96 months of usable housing history and classified 3-month prediction as structurally feasible.

Longer 12-month and 24-month predictive claims are not introduced because the current data does not support them.

## Target Construction

Price prediction target:

- `future_price`

The target is generated by shifting the price series forward within each LSOA.

Growth prediction target:

- `future_price_growth`

The target measures forward percentage price change over the configured horizon.

## Leakage Prevention

The training-data layer rejects:

- target columns
- future columns
- label columns
- prediction columns
- predicted-output columns
- explicitly forbidden source columns

Current raw price is excluded from the model feature set when it is the source used to construct the future target.

## Temporal Splitting

Training datasets use chronological splitting.

Default proportions:

- 70% training
- 15% validation
- 15% testing

Timestamp boundaries are used instead of random row splitting.

This prevents future observations from leaking into earlier model-development partitions.

## Reproducibility

The feature store produces:

- Parquet feature artifact
- JSON manifest

Each training task produces:

- `train.parquet`
- `validation.parquet`
- `test.parquet`
- `manifest.json`

The manifests record dataset dimensions, target definitions, feature columns, rejected leakage columns, and temporal split boundaries.

## Current Scope

Step 3 creates training-ready data infrastructure.

It does not claim that every predictive task is currently production-ready.

The predictive data-gap assessment remains authoritative regarding:

- limited historical depth
- repeated entity-period coverage
- feasible prediction horizons
- forecasting limitations
